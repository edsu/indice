# Web interface in Italian (i18n): design

Issue: #241. Date: 2026-11-06.

## Why

An Italian organization wants to run its own indice server to host its web archives, moving off a pywb + Solr setup. One operator runs the server; several curators add crawls, write annotations and describe collections; the public searches and replays what they publish. Everyone involved reads Italian, and the annotation features are a large part of why they are interested. Today every word indice shows is English.

Success: an operator sets one config value and every page, message and control their staff and visitors see is in Italian (unless a visitor's browser asks for another language indice has), with wording an Italian archivist finds natural. Adding a third language later means adding one translation file and nothing else.

## Goals

- The whole web interface can be served in Italian: home, search, collection, crawl, the curator workroom (`/manage`), login and the header, and the replay viewer's own chrome and annotation interface (`static/replay/viewer.html`, `viewer.js`, `annotations.js`).
- Text set by browser JavaScript is translated too (`static/assets/manage.js`, `editor.js`, and the replay scripts above).
- Error and status messages a person sees in the web UI are translated: error text the workroom displays from server responses, and indexing progress messages streamed to the add-crawl page.
- Plurals are grammatical in each language ("1 raccolta", "3 raccolte"). No more `crawl(s)`.
- Dates and numbers shown in the UI follow the language's conventions.
- Each visitor sees their browser's preferred language when indice has it, and the instance's configured language otherwise.
- `<html lang>` matches the served language on every page indice renders, including `viewer.html`.
- The AI-drafted collection description (`describe`) is written in the instance's language.
- English remains the configured default: an existing instance with no new config keeps serving English to every browser that doesn't prefer a language indice has.

## Non-goals

- A language switcher on the page, or a per-user language preference. A visitor whose browser asks for the wrong language cannot override it. Could come later (e.g. a cookie consulted before `Accept-Language`); the per-request language below makes that a small addition.
- The CLI, its output and `--help`. Only the operator sees these.
- The documentation site (indice.page).
- The vendored ReplayWeb.page code (`static/replay/ui.js`, `sw.js`). If ReplayWeb.page has its own language option, setting it to match is a welcome extra, not a requirement.
- Content curators write (annotations, descriptions, collection names): shown as written.
- The JSON API meant for scripts and other programs (`server/api.rs`): stays English, because clients may match on its messages.
- How search matches archived text (accents etc.): that is #244, separate and low priority.

## Anti-goals

- Breaking the single self-contained binary: translations are compiled in; no runtime files to ship or install.
- A half-translated page that looks finished: a key missing from the Italian catalog must be caught by a test, not discovered by a visitor.
- Translation scattered through Rust logic (e.g. hand-written `if n == 1` plural code per message).
- Archival terms translated loosely. The Italian draft is a starting point for review by the Italian user, not a final text.

## Decisions

Decided with Ed:

- **Language is chosen per request: the browser's language if indice has it, otherwise the instance's configured language.** indice matches the request's `Accept-Language` list against the languages it has catalogs for and uses the first match; with no match (or no header) it uses `site.language`.
- **The AI-drafted description uses the instance language (`site.language`), not the curator's browser**, because a description is part of the archive's record and should not change language with whoever pressed "draft". Ed may revisit this.
- **Italian is the first non-English language**, and Claude drafts the Italian text; the Italian user reviews the wording before it is considered done.
- **Scope is the whole web interface**, as listed under Goals.
- **Error chains: translate the outer sentence only.** Where the UI shows an error from the library (an `anyhow` chain printed with `{e:#}`, e.g. via `detailed_failure` in `server/auth.rs` or `ProgressEvent::Error` in `server/manage.rs`), the sentence indice wraps it in is translated ("Import non riuscito: …") and the chained technical detail stays as it is, English or whatever an upstream service sent. No structured error types for this work.
- **Draft Italian may ship before review**, so the work can land page by page across ordinary PRs and releases; the Italian user's review comes later and arrives as wording changes to `it.ftl`. With browser-based selection this means Italian-preferring visitors to *any* instance (app.indice.page included) see the draft Italian once it ships.
- **Every language indice has is offered on every instance.** An instance left at the default `en` still shows Italian to a browser that prefers Italian. There is no operator setting to restrict the offered languages (no `site.languages`); add one only if an operator needs it. Curator-written content is unaffected, and the rule stays one sentence: your browser's language if indice has it, otherwise the instance's.
- **Archival terms start as a best guess and get adapted.** There is no known existing Italian vocabulary to follow.

Claude's calls (Ed saw and agreed to these in outline; listed so they can be checked):

- **Config key**: `site.language` in the existing `site:` section (next to `name` and `tagline`), a language tag such as `it`: the fallback language when the browser asks for none indice has. Default `en`. An unsupported value is a startup error with a message listing the supported languages, not a silent fallback to English.
- **Negotiation**: `fluent-langneg` (same project as Fluent) matches `Accept-Language` against the available catalogs, so `it-IT` finds `it`. The chosen language travels to views on `Chrome`, built per request.
- **Caching**: every response whose text depends on the chosen language (HTML pages, `viewer.html`, and any UI-internal response carrying rendered text) sends `Vary: Accept-Language`, so a shared cache or proxy never serves one visitor's language to another.
- **Library**: Fluent (`fluent-bundle`, or `fluent-templates` if it fits better). Pure Rust, handles plural rules per language (via `intl_pluralrules`), and its `.ftl` file format is readable by non-programmer translators.
- **Catalog files**: one per language (e.g. `crates/indice-lib/locales/en.ftl`, `it.ftl`), embedded with `include_str!` or equivalent. English is the reference.
- **Key terms defined once**: the words for crawl, capture, collection, annotation, curator and the like are Fluent *terms* (`-raccolta = raccolta`, referenced as `{ -raccolta }`) at the top of each catalog, with a short comment on what each means in indice. When the Italian user prefers a different word, that is one edit, not a hunt through every message. (Terms that need different grammatical forms in Italian can use Fluent term attributes or variants.)
- **Completeness test**: a test fails if a non-English catalog lacks a message English has, or has one English doesn't, or if a message fails to parse. Another test checks every message key the code uses exists in English.
- **JavaScript strings**: the server puts the strings a page's scripts need into the page as JSON in a `<script type="application/json">` element, the pattern `viewer.html` already uses for its replay context (the CSP refuses inline script, not JSON data). Scripts read strings from there; there is no second catalog in JS.
- **Errors**: messages the server returns to the web UI and the UI displays (e.g. workroom actions that show `Error: …` from a response body, the busy text an annotation save can get back) are translated.
- **Where "the API stays English" stops**: at the endpoints documented as a public API in `site/src/content/docs/docs/reference/api.md` (`GET /api/search`, `GET /api/annotations`, the annotation and replay read endpoints, `/health`). That page already says the management write endpoints under `/api/` and their SSE progress streams are "an implementation detail of that UI rather than a stable public API", so their messages and event shapes may change: they can carry message keys and arguments for the page to render, or text rendered in the request's language. The annotation write endpoints are UI internals in the same sense.
- **Progress messages**: indexing phases are currently English strings passed from `indice-lib` through `IndexProgress::phase` (e.g. `"waiting for another import to finish…"`) and shown by both the CLI and the add-crawl page. The web side must show them in the language of the page that opened the stream and the CLI keeps English. Proposed shape: the library reports phases as data (an enum or a key plus arguments) and each consumer renders them, which matches the AGENTS.md rule that the library reports facts and the binary owns presentation.
- **describe prompt**: the built-in prompt tells the model which language to write in, filled from `site.language`. A custom `describe.prompt_file` is used exactly as the operator wrote it.
- **Ready for scripts and right-to-left languages, without building for them**: language tags are kept whole (`zh-Hant`, not `zh`), so Chinese can later have Simplified and Traditional catalogs and `zh-TW` matches `zh-Hant`; plural forms sent to JavaScript carry every category the language uses (Arabic has six), not just one/other; Fluent's bidi isolation marks are off for left-to-right languages and on for right-to-left ones; pages emit `<html dir>`. Converting the CSS to logical properties for a right-to-left language is separate work, done when one is added.
- **Dates and numbers**: Fluent does not format dates or numbers for a locale, so indice needs a small formatter of its own for both: dates the UI formats itself (e.g. `6 novembre 2026`) and numbers and sizes (`human_size` in `server/util.rs`; Italian uses `1.234` and `2,5 MB`). Month names and separators can live in the catalog; no ICU C dependency.

## Constraints

- Single binary, pure Rust (AGENTS.md). Any new dependency must compile without a C toolchain and its licence must pass `cargo deny`.
- `indice-lib` owns the views and therefore message lookup. Keep the added dependency surface small; message lookup is not a UI framework, but check it against the "library stays UI- and dependency-free" convention and say how it fits.
- CI checks: `cargo fmt`, `clippy -D warnings`, `build --locked`, `test --locked`. Commit `Cargo.lock`.
- Content Security Policy: no inline script; data goes in JSON script elements.
- `viewer.html` is filled by string replacement in `server/assets.rs` (`replay_page`), with a fixed fill order for safety (operator snippet first, archived URL last). New slots must keep that ordering argument intact. Its ETag is a hash of the filled output, so each language already gets its own ETag; it still needs `Vary: Accept-Language`.
- Docs describe how indice works now (AGENTS.md): README, DESIGN.md, the manage guide and the configuration reference under `site/src/content/docs/` must describe `site.language` and how to add a language.

## Tests

- Catalog completeness and parse tests (above).
- A server test: an instance configured with `site.language: it` serves Italian pages with `lang="it"`, including the viewer page.
- A server test: an unconfigured instance with no `Accept-Language` serves English with `lang="en"`.
- A server test: the same URL requested with `Accept-Language: it-IT,it;q=0.9` and with `en` returns Italian and English respectively, on an instance configured either way, and both responses carry `Vary: Accept-Language`.
- A server test: a browser asking only for a language indice lacks (e.g. `ja`) gets `site.language`.
- A plural test for at least one message in each language.
- Config test: an unsupported language is rejected at startup with a helpful message.

## Left to the builder

- Fluent crate choice (`fluent-bundle` directly vs `fluent-templates`) and how the bundle is passed to views (e.g. through `Chrome` / `Site`, which every page already gets).
- Message key naming scheme and how `.ftl` files are organized.
- Exactly how JS strings are selected per page (all strings vs per-page subset).
- How the progress-phase change is structured, within the constraint above.
- Where negotiation happens (a middleware/extractor vs in each handler), as long as every page and UI-internal response agrees.
- Order of work and how it is split into PRs; translating page by page is fine as long as each PR keeps the completeness test green.
